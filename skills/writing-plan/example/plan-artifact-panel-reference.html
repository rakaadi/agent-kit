Plan sections

Goal and Architecture
State the observable outcome and the boundaries that own it. Include material dependencies, version constraints and approved design choices. Give shared constraints, risks or runtime diagrams their own section when several tasks rely on them. Identify the source of confirmed decisions and the prerequisite for each unresolved choice.
Execution Metadata and section navigation
Record the source requirement, baseline and any execution agreement shared by the tasks. Link to the handoff for current state. Give each substantive section a stable fragment link in the navigation.
Progress Tracking
Keep the current checkpoint near the opening. A returning agent should be able to follow its next-focus link to a task, that task’s verification row and any recorded evidence. See the worked handoff below.
File Structure
Map affected paths to responsibilities and owning tasks. Distinguish inspected files, proposed additions and conditional changes. For an unsettled design, name the boundary and the task that will establish the path.
Execution Flow
Use the ledger dependencies to draw the Mermaid graph. Label nodes with task IDs and explain what allows parallel work or forces serial work, including shared file ownership. Keep Mermaid source and a readable sequence alongside the offline rendering. Regenerate the diagram after changing an edge.
Task Ledger
Use one row per reviewable outcome. Each row is an independently linkable unit in both the source and the browser. Use phase labels when they carry sequencing information. See ledger fields.
Verification Matrix
Keep planned commands and required manual checks in this table. Identify each task or integration scope, the working directory or prerequisites when relevant, and the observable result. Cross-link the scope and task rows. A check shared by several tasks can have one row with multiple task links.
Out of Scope
Name adjacent work explicitly excluded from this handoff. Carry forward existing scope boundaries, decisions, design artifacts and execution evidence when converting a plan.

Ledger fields

Task / dependency
Use the task ID as the row’s id. Show its title and link each direct prerequisite by ID. Use “Nothing” for a runnable root. Link to the same ID from the handoff and verification matrix so the browser highlights the referenced row.
Change and instructions
Keep the outcome and essential context visible. Put steps, reuse constraints, failure behavior and illustrative diffs inside native <details> with an Instructions summary. Label a diff as illustrative. List required skills beside the disclosure when applicable. Keep blockers affecting readiness visible in the dependency or handoff text.
Produces
Name the changed files, evidence or design artifact another task will consume. Keep each task’s instructions, outputs and acceptance on separate source lines so a local edit produces a focused diff.
Acceptance and review
Describe what proves the task complete and link to its verification row. Add a visible Advisory Review paragraph only where human judgment adds something checks cannot establish. Name the surface, judgment and validation limit. Keep at most three focus items. Put explicitly required human checks in the matrix and material pending decisions in prerequisites.

Session handoff

Start a fresh plan with the values shown in the skeleton. Use Not started, In progress, Blocked or Completed for current status. Maintain dates and executed task IDs newest first. Add “Unplanned necessary work” only when it occurs.

At a partial stop, record what changed, what was actually verified and the first remaining action. For parallel tasks, identify active assignments and which work is still available.

Execution records

When work produces evidence worth retaining, append a dated record with the task ID, revision or environment, actual result and remaining gaps. Link the handoff or task to that record. Keep past checkpoints dated so the handoff can advance without rewriting history.

For a collapsible record, place its target ID on the content inside the disclosure. A fragment link can then open the record directly. The example checkpoint above links to this entry.
