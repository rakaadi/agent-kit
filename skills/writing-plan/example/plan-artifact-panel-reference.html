How To Use

Stable panel intent

Place each concept in its matching skeleton panel. Add a top-level section only for distinct content.

Header Summary

Orient the reviewer at a glance.

Carry the title, goal, architecture, and execution metadata in a compact first screen. Record material technology choices in Architecture or the relevant task.

  • Keep visible: title, goal, architecture, status or scope metadata.
  • Suggested layout: summary cards plus a metadata card.
Table of Contents

Keep long plans skimmable.

Mirror the real sections with anchor links so reviewers can jump without losing context.

  • Keep visible: anchor links matching the actual sections.
  • Suggested layout: sticky sidebar or compact top nav.
Locked Decisions

Record confirmed implementation constraints.

Record a decision as locked only when supported by an explicit requirement, established constraint, or approval. Keep proposals and pending decisions distinct.

  • Keep visible: decision name, chosen constraint, and its source.
  • Suggested layout: two-column comparison table.
Current-State Hotspots

Explain why the refactor exists.

Point to the current files, flows, or ownership tangles that create the migration pressure.

  • Keep visible: file or flow, current responsibility, reason it matters.
  • Suggested layout: table or tightly structured cards.
Target Module Shape

Show the destination structure.

Make the proposed file layout, key boundaries, and public surface concrete where established. Identify pending design and its dependent work where the shape remains unresolved.

  • Keep visible: folder shape, boundary notes, planned public surface when applicable.
  • Suggested layout: two-up panels plus a monospace API block.
File Inventory

Identify affected files and responsibilities.

Distinguish inspected existing files, proposed new files, and boundaries awaiting design. Show known changes and their purpose without presenting speculative paths as final.

  • Keep visible: established paths, proposed files, responsibilities, and prerequisites for unresolved boundaries.
  • Suggested layout: create and modify tables in a two-up layout.
Execution Flow

Show order, gates, and parallelism together.

Show task dependencies with Mermaid and task IDs, alongside readable sequencing notes. Keep runtime behavior diagrams in the relevant design context.

  • Keep visible: dependency order plus nearby text that preserves the same meaning.
  • Suggested layout: Mermaid task graph with sequencing notes that remain readable without JavaScript or network access.
Phase Sections

Turn the plan into executable work.

Group tasks by a real rollout phase or workstream so review tracks how the work lands.

  • Keep visible: phase purpose and a repeatable task-card structure.
  • Suggested layout: one panel per phase with a vertical stack of cards.
Task Card

Make each task independently reviewable.

Show the execution unit and its metadata together so reviewers can assess its scope.

  • Keep visible: task ID, title, description, produces, acceptance, and exactly one dependency marker.
  • Suggested layout: chips at the top, one-to-three-sentence description, selective annotated diff with explicit constraints or a checklist, metadata grid at the bottom.
  • Label diff sketches as illustrative; preserve failure behavior and prerequisites without implying approval of pending design.
  • Keep verification commands and expected results in the plan-level Verification Matrix.
  • When human judgment is especially valuable, add a Human Review Focus pill and matching content box. Omit both when no focus applies.
Human Review Focus

Point human judgment at the narrowest valuable surface.

Use the advisory focus rules in SKILL.md: name the surface, judgment, and validation limit. Record unresolved material decisions as prerequisites and explicitly required human checks in verification.

  • Keep visible when present: the target surface, the judgment to apply, and why agent or automated validation is insufficient.
  • Suggested layout: a pill after the dependency marker and a slightly wider third metadata box beside Produces and Acceptance.
  • Use at most three concise focus items; split or prioritize instead of recreating line-by-line review.
Verification Matrix

State the evidence needed for acceptance.

Use the smallest meaningful checks while preserving mandatory repository checks. Distinguish task checks, final integration checks, and explicitly required human checks.

  • Keep visible: task ID or integration scope, checks, commands or manual steps, expected results, and relevant environment notes.
  • Suggested layout: one plan-level verification table; keep task cards free of Verification fields and run-command bullets.
Progress Tracking

Keep execution state visible without reading every task card.

Show execution state, recent tasks, and blockers for a fresh or in-flight handoff. Record necessary work outside the task list when it occurs.

  • Keep visible: current status, started on, completed on, last executed tasks, current blocker or next focus, and unplanned necessary work when it exists.
  • Suggested layout: compact metadata grid plus a short execution-notes list.
Out of Scope

Protect the plan boundary.

Name adjacent work excluded from the plan to keep execution within scope.

  • Keep visible: explicit exclusions and a source-plan reference when converting an existing plan.
  • Suggested layout: numbered list plus a short source reference note.
Optional Panels

Add only when the source plan actually contains new information.

Add risks, open questions, rollout notes, or ADR links when they carry distinct content beyond the existing panels.

  • Keep goal, architecture, and task content in their existing panels.
  • Omit optional panels such as locked decisions or hotspots when empty. Preserve all required sections from SKILL.md.
  • Extend the existing skeleton by default.
