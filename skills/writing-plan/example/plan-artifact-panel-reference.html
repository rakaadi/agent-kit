Panel Purpose Map

Plan Artifact Panel Reference

This page extracts the main job of each panel from the working Firebase artifact so agents can keep the structure firm while still extending the content for a new plan.

How To Use

Stable panel intent

Do not invent new top-level sections just to rephrase the same content. If the source plan contains one of these concepts, extend the matching panel from the skeleton instead of moving it somewhere else.

Header Summary

Orient the reviewer before the scroll starts.

Carry the title, goal, architecture, tech stack, and execution metadata in a compact first screen.

  • Must stay visible: title, goal, architecture, tech stack, status or scope metadata.
  • Good shapes: summary cards plus a metadata card.
Table of Contents

Keep long plans skimmable.

Mirror the real sections with anchor links so reviewers can jump without losing context.

  • Must stay visible: the real section list, not a decorative outline.
  • Good shapes: sticky sidebar or compact top nav.
Locked Decisions

Freeze the implementation constraints.

This panel records the decisions that later tasks are not allowed to drift away from.

  • Must stay visible: decision name and chosen constraint.
  • Good shapes: two-column comparison table.
Current-State Hotspots

Explain why the refactor exists.

Point to the current files, flows, or ownership tangles that create the migration pressure.

  • Must stay visible: file or flow, current responsibility, reason it matters.
  • Good shapes: table or tightly structured cards.
Target Module Shape

Show the destination structure.

Use this panel to make the future file layout, key boundaries, and public surface concrete before task detail begins.

  • Must stay visible: folder shape, boundary notes, planned public surface when applicable.
  • Good shapes: two-up panels plus a monospace API block.
File Inventory

Lock the file-level work slices.

A reviewer should leave this panel knowing what gets created, what changes, and what will be deleted later.

  • Must stay visible: exact file paths and the purpose of each change.
  • Good shapes: create and modify tables in a two-up layout.
Execution Flow

Show order, gates, and parallelism together.

Combine dependency flow and sequencing guidance into one readable section before task cards.

  • Must stay visible: dependency order plus nearby text that preserves the same meaning.
  • Good shapes: Mermaid or static graph with sequencing notes beside it.
Phase Sections

Turn the plan into executable work.

Group tasks by a real rollout phase or workstream so review tracks how the work lands.

  • Must stay visible: phase purpose and a repeatable task-card structure.
  • Good shapes: one panel per phase with a vertical stack of cards.
Task Card

Make each task independently reviewable.

This is the smallest execution unit. Keep the metadata obvious so reviewers can reason about scope without opening another section.

  • Must stay visible: task ID, title, description, produces, acceptance, and exactly one dependency marker.
  • Good shapes: chips at the top, instructions in bullets, metadata grid at the bottom.
Verification

State the release gate explicitly.

Keep the verification checklist or matrix visible so the plan does not treat correctness as implied.

  • Must stay visible: flow, expected behavior, special environment notes.
  • Good shapes: verification table or concise checklist.
Out of Scope

Protect the plan boundary.

Name the tempting adjacent work that this plan will not absorb, so execution does not widen silently.

  • Must stay visible: explicit exclusions and the source-plan reminder.
  • Good shapes: numbered list plus a short source reference note.
Optional Panels

Add only when the source plan actually contains new information.

Risks, open questions, rollout notes, or ADR links can be added, but only when they carry new semantics that do not already belong in one of the stable panels above.

  • Do not create new panels just to restate goal, architecture, or task information in a second format.
  • If the source plan has no locked decisions or hotspots, the related sections may be omitted, but the task, verification, and out-of-scope sections remain required.
  • When in doubt, extend the existing skeleton rather than designing a new information architecture.
